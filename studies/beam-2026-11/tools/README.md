# Study harness (tools)

These files are the harness of the BEAM 2026-11 study: they feed a BEAM conversation to a Claude
Code "student" running a local model, one exchange at a time, and record every turn. They are
research scripts, not product code. The run scripts are kept as the record of how the practice
runs were executed.

## Requirements

- Python 3 with `pyarrow` (the scripts that read the dataset).
- Claude Code (`claude` on `PATH`).
- Ollama serving the model (default endpoint `http://localhost:11434`; override with `BEAM_OLLAMA_URL`).  <!-- privacy-scan: allow (Ollama's documented default endpoint) -->
- The BEAM 100K parquet file from Hugging Face. It is not redistributed in this repository.
- For the ENGRAM arm only: a checkout of the ENGRAM source that holds `tools/install.sh`.

## Scope of this harness

The harness renders **exam format v2 only** (the proctor marker, the reading-material delimiters and
the relabelled speakers; see `../protocol/exam-room.md`). Two parts of the planned E3 design are not in it yet:
E3's brief sentence, and the user-level exam line that both arms are to receive. The run scripts record the
practice runs that were executed; they do not run E3.

## `feed.py`

The per-turn `--resume` driver used for the early practice runs, and the single source of the exam
brief and of how a conversation is rendered. It holds the exam brief (`BRIEF`), the proctor marker
(`PROCTOR`), the per-exchange line (`TURN_LINE`), the question prompt prefix (`QUESTION_PREFIX`),
`render()` and `exchanges()` (which turn a BEAM conversation into one prompt per user/assistant
exchange), and `unload()` (asks Ollama to unload the model so a resident model does not block the
next run's GPU reservation). As a program it feeds one conversation to a Claude Code session, one
exchange per `claude -p` call (`--resume` after the first), and optionally asks probing questions.

- Inputs: `--arm-home DIR --out DIR --conv N --turns K [--questions Q] [--model M] [--turn-timeout S]`; `BEAM_PARQUET`.
- Outputs: `<out>/turns.jsonl` (one summary line per turn); progress on stdout.

## `feed2.py`

The driver used by every run script. One persistent Claude Code process per run
(`--input-format stream-json --output-format stream-json`), so session-start hooks fire once. It
imports `BRIEF`, `PROCTOR`, `QUESTION_PREFIX`, `exchanges` and `unload` from `feed.py`, so the two
files must stay in one directory. It holds `FACT_SHEET` and `NUDGE` (the fixed setup texts). Phases in one session: optional first-session setup (a fixed fact sheet, then a
fixed nudge per further question), reading (brief plus one exchange per message; the student ends
each with NEXT), optional `/compact`, then probing questions and any proctor-written practice
questions.

- Inputs: `--arm-home DIR --out DIR --conv N --turns K [--questions Q] [--first-session] [--setup-only] [--setup-rounds R] [--force-compact] [--ask TEXT ...] [--model M] [--turn-timeout S] [--env KEY=VALUE ...]`; `BEAM_PARQUET`.
- Outputs: `<out>/events.jsonl` (every stream event), `<out>/turns.jsonl` (per-turn summary), `<out>/stderr.log`.

## `ask-proctor`

The escalation command available to the student inside the exam room, for problems with the exam
environment only (never benchmark content). It writes the question to `$PROCTOR_DIR`, waits for an
answer file written by the proctor, prints it, and appends every question and answer to
`$PROCTOR_DIR/log.tsv` with UTC times. The feeders put this directory on the student's `PATH`.

- Inputs: the question as arguments; `PROCTOR_DIR`; optional `PROCTOR_TIMEOUT`.
- Outputs: `$PROCTOR_DIR/q-<id>.txt`, `$PROCTOR_DIR/log.tsv`; exit 3 on timeout.

## `patch-core-alwaysload.py`

Sandbox-only patch used by the E2 run. Marks six ENGRAM tools (`engram_add_observation`,
`engram_inspect`, `engram_query`, `engram_derive`, `engram_supersede`, `engram_checkpoint`) as
`anthropic/alwaysLoad` by inserting one `meta=` line after each tool's `@mcp.tool(` decorator in an
installed copy of `server.py`, so Claude Code does not defer them behind tool search.

- Input: path to a `server.py` copy (argument 1). Patches it in place.
- Output: one line per tool; exit 1 unless all six were patched exactly once.

## Run scripts

**RETIRED (the sandbox launch module is the only door).** `pilot-run.sh`, `run-engram-full.sh`, `run-v2-both.sh`,
`run-e2-core.sh`, `run-e1-alwaysload.sh` and `vanilla-hello.sh` start a student outside `sandbox_launch.py`, so each now
carries a `# RETIRED-LAUNCHER` marker on its second line and refuses at once (exit 2, a `RETIRED:` line on stderr, nothing
created). They stay as the record of how the practice runs were made; a cell runs each one. Student sessions are started
by `p1-session.py` through the module (section below). The description that follows is the record of the retired scripts.

All five fail at once, with a message, if a required variable is unset. Each deletes and recreates
its HOME directories under `$BEAM_WORK`, so give it a scratch location outside any git repository.

- `run-engram-full.sh`: ENGRAM arm, full practice sequence. Fresh install, first session as its own session, then the exam in a new session (3 exchanges, forced `/compact`, 2 questions).
- `run-v2-both.sh`: format-v2 repeat, vanilla arm then ENGRAM arm (3 exchanges, forced `/compact`, 2 practice questions, same text in both arms).
- `run-e1-alwaysload.sh`: ENGRAM arm with the plugin's MCP server set to `alwaysLoad` (patch applied to `.mcp.json`); setup once, snapshot, three independent exams.
- `run-e2-core.sh`: ENGRAM arm with only the six core tools patched to `alwaysLoad` via `patch-core-alwaysload.py`; setup once, snapshot, three independent exams.
- `vanilla-hello.sh`: smoke test of vanilla Claude Code on the local model in an isolated HOME (see `BEAM_HELLO_DIR`).

Outputs (all but the last go under `$BEAM_OUT`): install logs and `run-*` directories as produced
by `feed2.py`; `vanilla-hello.sh` writes `vanilla-hello<TAG>.json` and `.err` into `$BEAM_HELLO_DIR`.

If a GPU reservation wrapper is needed on your host, put it in front of `$PY -I $BEAM_TOOLS/feed2.py`
yourself; the scripts here run the commands exactly as the practice runs did.

## `check-port-identity.py`

Checks that a ported copy of `feed.py`/`feed2.py` shows the student exactly what a reference copy
shows: sha256 of the brief, proctor marker, per-exchange line, setup fact sheet and nudge, and of
`render()` and `exchanges()` output on a small synthetic conversation, the question prompt prefix, plus
a comparison of every string literal in the source as a multiset in both directions (so a change to one
of two copies of a duplicated literal, or an extra literal in the port, is reported). Usage: `check-port-identity.py PORTED_DIR` compares a copy's student-visible components with the committed pin in `data/pinned-runs-feed.json` (anyone can run it); `check-port-identity.py REFERENCE_DIR PORTED_DIR` runs the full comparison and refuses (exit 2) a reference whose feed.py does not hash to the pinned sha256; `--reference-sha` overrides the pin with a printed warning. Exit 0 =
identical.

## `feed4.py`, `setup-id.py`, `coverage.py`, `gate-input-evidence.py`

`feed4.py`: the gate runs' feed script plus `--per-round K` (speed pilot P1) and `--dump-plan`. `setup-id.py`: the
setup id by content, with the import walk (every study-local module the feed script imports must be a component).
`coverage.py`: the pilots' note-coverage attribution, its controls, and the per-run measures. `gate-input-evidence.py`:
shows, byte for byte, that a run's student received the messages its own `feed.py` builds. Each file's docstring has
its usage; the tuning log has their outputs.

## Answering harness (P1): `--question-file`, `answer-delivery-check.py`, `plant-control.py`, `control-source-check.py`

`feed4.py --question-file F` delivers a frozen list (a JSON list of `{"id", "question"}`) in file order, once each, after
the optional `/compact`, one message per item (`PROCTOR + " " + QUESTION_PREFIX + question`). An answering run is
`--resume SESSION --turns 0 --force-compact --question-file F`; `--dump-plan` shows exactly `[compact, q1..qN]`. It is
refused (exit 2, before any student process or model unload) without `--resume`, with `--setup-only`,
`--first-session`, `--questions` or `--ask`, with duplicate ids, an empty
question, an empty list, or a file that is not a list of such objects. Each question's turn record carries
`"kind": "question"` and its `"id"`. Without the flag the plan and the turn records are unchanged.

`answer-delivery-check.py --turns RUN/turns.jsonl --questions F --session SESSION`: PASS (exit 0) only if every turn
carries the resumed session id, exactly one compact turn precedes the first question, every id of F appears once in file
order, and there are no other question turns and no reading turns. Each failure is printed; exit 1 on any.

`plant-control.py --home COPY --builtin-fact T --engram-fact T --absent-fact T --evidence-dir DIR`: the two-channel
control, for a **disposable copy** of an arm home only (refuses without `COPY/.disposable-copy`, under `P1_PROTECTED`,
with an evidence dir inside `COPY/work`, or with a fact shorter than 6 characters). The built-in fact goes in as one
markdown file in the arm's memory folder; the ENGRAM fact through `engram_observation._add_observation_impl` (what the
`engram_add_observation` tool calls), imported in-process from the copy's own plugin, with its evidence file in DIR. It
also lists the note in the folder's `MEMORY.md` by one neutral appended line in the format of an existing line (exit 2 if
there is no `MEMORY.md`; `--question TEXT` exits 2 if that line holds a content word of the question); the observation is
embedded by default through the copy's own embedder (`--no-embeddings` opts out; exit 2 if the model cannot load). It
then checks read-back, that no fact is in any transcript, cross-absence between the two channels, that the absent fact
is nowhere, and the per-table row counts before and after. Run it with the python of the copy's ENGRAM venv. Exit codes: 0 all checks pass, 1 a check failed, 2 refused, **3 a `P1_PROTECTED` entry changed during the run** (a snapshot of every protected entry is compared with a re-walk on every exit path after the pre-write scan; each changed path is printed, then `PROTECTED CHANGED: n path(s)`; this overrides 0, 1 and 2, and a clean run prints `protected unchanged: ...`). It reports a write, it cannot undo one.

`plant-control.py` **ENGRAM-only mode** (P1 control 2 on an end state whose built-in folder is empty): `--builtin-fact` is
optional. Without it the tool plants the ENGRAM fact only and prints `mode: engram-only (no built-in plant)` before any
write (`mode: both channels` otherwise). It writes nothing under any built-in memory folder; a missing `MEMORY.md` or
memory folder is not a refusal; `--question` is refused (exit 2, it only qualifies the index line). A new check,
`memory folders unchanged`, proves the set of memory folders found is the same after the write (a newly created folder
FAILS) and that every entry of every memory folder is the same: files and directories, with type, mode and, for a file,
sha256 (a new empty directory or a chmod FAILS; zero folders is reported as `0 folders, unchanged`; exit 1 on FAIL). The checks that need the built-in fact print `SKIP (no built-in plant)`, never PASS, and do
not change the exit code; all other checks and the exit-3 post-condition run as in the two-channel mode, which is
unchanged when `--builtin-fact` is given.

`control-source-check.py --events E --turns T --controls C`: for the three control questions (one per channel), decides
each planted fact on REACHABILITY, not on the answer (the final rule, design owner's rulings of 2026-11-18). **Design
principle: every approximation errs toward FAIL for the clause it serves; the module docstring applies it as a class rule:
it ENUMERATES the seven exemption sites S1 to S7 (every place something is decided NOT to count), and for each names what
it exempts, the positive known-shape evidence it requires, and that an unknown or off-shape input COUNTS (cells
`test_r3_s1_*` to `test_r3_s7_*`).** An engram/folder fact PASSES iff (a) a read
through its intended channel, named by STORAGE (a pinned ENGRAM read tool; or any call whose target is inside the memory
folder, the folder of the control's `folder_file`: a Read, a Grep/Glob `path`, a Bash command naming a path inside it,
`~` / `$HOME` / `${HOME}` resolved to the home taken from `folder_file`, quote-split words such as `"$HOME"/.claude/...`
joined), in a turn after the compaction returned the token
in that call's tool result, (b) the student's own query text echoed back never counts: for (a) every occurrence of every
string of the call's own input (`payload_json` decoded) is stripped from the result first (a stored value equal to the
query is stripped too, toward FAIL); for (c) and (d') only the top-level `query` field of an `engram_query` / `engram_surface` result is stripped (the
one echo the server is known to produce; an ENGRAM result recorded in Claude Code's envelope `{"result": "<inner JSON as a string>"}`, exactly one key whose value is a string that parses as JSON, is read as its inner object, here and for the created ids of (c'), and no other shape is unwrapped); every other tool, a result that does not parse and a result without that field
is not stripped, so an `engram_list` contains-filter on the token that returns one stored copy is a return, and so is a
query that is exactly the token whose result also holds a stored copy; a Grep, Bash or Read result is never stripped, (c)
no read through the other channel returned the token anywhere in the session (for a folder control the other channel is
every tool of the pinned ENGRAM server except its known writes, the `readOnlyHint=false` ones, so `engram_history` and
`engram_diagnose` count and an unknown tool counts), except (c') a returned item the tool can IDENTIFY as one the student wrote after its first
intended read: for the ENGRAM channel the result is parsed and every dict holding the token must carry the id of a node the
student's own creating tool reported created after that read, under that tool's own key and with status "created"
(`engram_add_observation` `observation_id`, the batch's `results[].observation_id`, `engram_derive` `derivation_id`,
`engram_add_conjecture` `conjecture_id`, `engram_ask` `question_id`, `engram_add_definition` `definition_id`; the keys are
cited to the plugin source in the code), with no token outside those dicts; `engram_supersede`, `engram_contradict`,
`engram_retract` and every other tool create no excusing id, and no bare `id` or generic key is read; for the
folder channel the read must be of a file the student itself created with a Write (absolute path, result "created
successfully") after that read, no earlier call having named it (an Edit/MultiEdit of a file is never excused, a grep of the whole folder is not excused); a `note:` names the
node ids or the file; a pre-existing item, an unparseable result or any other return FAILs, and (d) the evidence file or
the run directory (the optional per-control `run_dir`) was not opened before that first read (opened after it is noted,
not void); an opening is a FILE-CAPABLE call, by default-deny: every call except `ToolSearch`, `TodoWrite`,
`ExitPlanMode`, `EnterPlanMode`, `AskUserQuestion` and any tool of the pinned ENGRAM server (so `Task`, `Agent`,
`WebFetch`, a tool of another MCP server and unknown tools count) that names them or that returns the token from a path outside both channels, while a path in an MCP tool's
arguments is only a mention. The answer is printed beside the verdict and decides nothing: a refusal that quotes the token
passes only if a channel read returned it. Other tool kinds are listed and neither pass nor fail. Stated bound (S7): a folder target the checker cannot resolve (a
relative path, a glob, a variable other than HOME, a subshell path, a Grep with no `path`) is not seen, and a `Task` or
`Agent` subagent that reads the memory folder returns the token with no folder target in this stream, so for the engram
control it is a note at most. It never decides abstention for the `none` control.

Cells: `tests/` (`pytest`; `BEAM_PY` = a python with pyarrow, `P1_ENGRAM_PLUGIN` = an ENGRAM plugin tree for the plant
cells). Synthetic fixtures only: no student model, no Ollama, no real arm home.

## Session launcher (P1): `p1-question-file.py`, `p1-session.py`

`p1-question-file.py --list F --expect-sha256 H [--exclude ID[,ID]] --seed N --out JSON`: builds the frozen question
file from the key-fact list (rows `ID | exchange | style | QUESTION || GOLD`). The question text only, never the gold; ids
sorted, then `random.Random(N).shuffle`; byte-identical for the same inputs; prints the count, the order and the JSON's
sha256. Exit 2, nothing written, on a wrong list hash, a repeated id, an `--exclude` id not in the list, an unparsable
row, or an existing `--out`.

`p1-session.py --end-state PATH --session ID --label NAME --question-file F --components F [--plant-builtin T
--plant-engram T --plant-absent T [--plant-question TEXT]] [--dry-run]`: answers the question file on a disposable copy of
a preserved end-state home, placed at the arm-home slot path so the run's session resumes. Environment (all required, no
host path in the file): `BEAM_PY`, `BEAM_ARM_HOME` (the slot), `BEAM_RUNS_DIR`, `BEAM_PARQUET` (the dataset file feed4.py
reads; it must be an existing file whose sha256 starts with the prefix `studies/beam-2026-11/PROVENANCE.md` registers, which the launcher checks in step 1 by streaming the file, as the reading runs' `pilot-run.sh` did; `setup.txt` records the full sha256), `P1_PROTECTED` (the preserved homes, one of
which is `--end-state`). A plant set is either all three of `--plant-builtin --plant-engram --plant-absent` (optionally
`--plant-question`) or exactly `--plant-engram --plant-absent` (engram-only, for control 2: plant-control.py runs without
`--builtin-fact` and writes nothing under any built-in memory folder); any other combination, and `--plant-question`
without `--plant-builtin`, is refused in step 1. `setup.txt` records the plant mode on its own line. Every refusal (exit 2) in step 1 happens before anything is touched: no process killed, no copy,
no directory made. One refusal comes later: step 4 refuses if the aside path already exists, after the slot processes have
been stopped; no protected path is touched either way. It never deletes (an existing slot is moved aside),
hashes the store and the built-in memory files of every protected home before and after, and exits 5 with
`PROTECTED CHANGED` if any differ. The exit-5 guarantee holds whenever the process gets to decide its exit (including
KeyboardInterrupt, SystemExit and other exceptions); a SIGKILL, power loss or machine failure between the copy and the
final check leaves no exit code at all. Outputs under `BEAM_RUNS_DIR/p1-LABEL`: `before-hashes.txt`, `after-hashes.txt`,
`plan.json`, `run/`, `transcripts/`, `delivery.txt`, `setup.txt`. Exit codes: 0 good, 1 delivery check failed, 2 refused,
3 copy, plan check or feed4 failed, 4 plant failed, 5 a protected home changed. The step list, the store-hash method and the
test-only hooks (`P1_FEED4`, `P1_PLANT_CONTROL`, `P1_UTC_STAMP`, `P1_AFTER_COPY_HOOK`, `P1_TEST_RAISE`, `P1_EXPECTED_PARQUET_PREFIX`; the last replaces the registered dataset prefix and `setup.txt` says so on its `dataset check:` line) are in its docstring.

`p1-session.py --continue-reading --start N --through M --per-round K --save-end-state PATH --expect-store-sha256 H [--expect-serving FILE]` (with `--end-state --session --label --components`, no question file, no plant flag; P1b): resumes the end state's session on the disposable copy and feeds READING rounds for exchanges N..M of conversation 9 (`--through` is the last exchange; feed4's `--turns` is the inclusive end index), then saves the resulting home as a new end state with its hashes in `PATH.hashes.txt` (both created exclusively at save time, the saved copy link-checked as the next run will check it, and only paths this run created are ever removed on failure; a failure to prove the protected homes unchanged that is not a difference prints `AFTER-HASHES UNAVAILABLE` and is exit 3, never `PROTECTED CHANGED`). Refuses (exit 2) a start off a round boundary, a partial last round, a store hash that is not the expected one, a save path or hashes path that exists or is equal to, inside or containing any path the launcher creates or protects (the run directory, the aside path, the slot, every protected home; one function, `launcher_paths`, is the single source and a test binds it to what a dry run really creates), and a serving setup that differs from `--expect-serving`; records the model server's version and the model digest in `setup.txt` (so `--dry-run` in this mode also needs a live model server: the serving setup is recorded at start, by design); checks that the continue plan is byte-equal to a full run's messages for the same exchanges before any student run; checks delivery with `reading-delivery-check.py --turns RUN/turns.jsonl --plan PLAN.json --events RUN/events.jsonl --session ID` (the answering check refuses reading turns by design). Cells: `tests/test_p1_continue_reading.py`, `tests/test_reading_delivery_check.py`.

## Student sandbox: `student-sandbox.sh`, `sandbox-forward.py`

A process boundary around the student (both arms). `student-sandbox.sh` must be the file named `claude` in a directory put FIRST on `PATH`, so `feed4.py`'s `Popen(["claude", ...])` starts it. **`sandbox_launch.py` does that, and everything else the run script must do, in one place, and is the only door** (next section); the older practice launchers are retired. It checks and prepares outside the box, then `exec`s `bwrap`; from the student's first instruction on, the student and everything it spawns live inside new PID, network, IPC and UTS namespaces. The feeder is not boxed and keeps reading the dataset. It needs `bwrap` (0.9.0 or newer: `--size`, `--ro-bind-fd`, `--ro-bind-data`, `--cap-drop`, `--seccomp`), `/usr/bin/python3` (standard library only), unprivileged user namespaces and a systemd user manager that can start a transient scope with the `pids` and `memory` controllers delegated (`systemd-run --user --scope`; the box's process and memory caps below); it never uses `socat`. It is Linux-only (bash 4 or newer, `/proc`, `bwrap`, systemd): on any other system every cell that runs the wrapper skips with one named reason instead of failing, and the pure-Python framing and allow-list cells run everywhere.

| Variable | Meaning |
|---|---|
| `SANDBOX_SLOT` | The benchmark home (the student's `HOME`): an existing directory, bound read-write at its own path. Validated by the class rules below. The caller's own `HOME` must resolve to it (`realpath` equal; a symlink to the slot or a trailing slash passes): the environment is passed through unchanged, so a different `HOME` would point at a path that does not exist inside the box, and the wrapper refuses instead. |
| `SANDBOX_BINARY`, `SANDBOX_BINARY_SHA256` | The pinned Claude Code binary and its full sha256. The binary is opened once, hashed from that open file, and THAT descriptor is bound read-only (`--ro-bind-fd`) at the file's resolved path, as the last mount: the file hashed is the file bound, and nothing mounted before it can shadow it. A mismatch is a refusal. Only the binary file is bound, never its directory (its siblings are invisible). |
| `SANDBOX_RO_BINDS` + `SANDBOX_RO_ROOT`, `SANDBOX_RW_BINDS` + `SANDBOX_RW_ROOT` | Optional extra binds: colon-separated absolute directories, bound read-only / read-write at their own resolved paths. Each ROOT is required with its binds, and every entry must lie inside its root after `realpath` (an allow-list by declared roots, never a list of bad names). Every entry must exist and be a directory. Every extra bind appears on the launch line. |
| `SANDBOX_PROTECT` | REQUIRED. A colon-separated list of absolute paths that must exist (files or directories): the dataset file and the key-list directory. No slot, root or entry may equal one, contain one, or lie inside one. An unset or empty value is a named refusal, as is an entry that is empty, relative or missing. (It replaces the earlier `BEAM_PARQUET` special case: a guard that skips itself when its variable is absent is not a guard.) |
| `SANDBOX_MODEL_HOST`, `SANDBOX_MODEL_PORT` | The model endpoint as the host sees it (a port of 1024 or above: the listener inside the box is unprivileged). Inside, the student keeps using `localhost:<port>` unchanged. |
| `SANDBOX_MODEL_ALLOW` | Required unless `SANDBOX_MODEL_LEARN=1`. Comma-separated `METHOD /path` entries: an exact path, or a prefix when it ends in `*` (for example `POST /v1/messages, GET /v1/models, POST /api/*`). The outer forwarder forwards a request only if it is on the list. |
| `SANDBOX_MODEL_LEARN` | `1` allows every request the forwarder can frame and logs each request's METHOD and PATH only (never a body, never a query string) to `SANDBOX_LOG`, which it then requires. The pilot uses it once to learn the harness's real set; the registered run fixes the list in `SANDBOX_MODEL_ALLOW`. Any other non-empty value is a refusal. |
| `SANDBOX_LOG` | Optional file outside the box: one `wrapper-launch` line per launch (the sha256 of the wrapper script file and of the forwarder, each taken at start (bash reads a script as it runs, so the wrapper hash is of the file on disk at launch: it records what was there when the run started); the forwarder is COPIED once into the run's private socket directory (mode 700, same lifetime and cleanup), and the hash, the helper subcommands, the outer forwarder and the file the box is given at `/run/sandbox-forward.py` are all that copy, so the file hashed is the file that runs; the name of the box's systemd scope, `scope_unit=student-sandbox-<wrapper pid>-<random>`; the model mode, `learn` or `allow`, and the allow-list's entry count; whether `SANDBOX_TEST` was set; every effective cap; the masked `/etc` file count), one `fwd-conn` line per bridge connection (open and close epoch seconds, bytes each way; never payloads), one `box-cgroup` line per run, written by the outer forwarder at exit (`box-cgroup scope=<unit> oom_kill=N memory_max_events=N pids_max_events=N polls=N last_poll_age_s=X`, or `box-cgroup unavailable reason=...` if it never found the box's cgroup: never silent), one tagged line per refusal or bridge fault (a `fwd-deny`, `fwd-refuse` or `fwd-fault` line carrying `kind=`: see "Refusal lines: the four counts" below; never a body, never a query string), and in learn mode one `fwd-req` line per request and a `fwd-learn-max` line (the largest request, the most concurrent connections and the most buffered bytes seen so far; the last such line holds the run's maxima). |
| Caps (no variable outside test mode) | The trusted side of the bridge, PROVISIONAL until the wrapper-cost pilot's learn mode has recorded the real maxima (the harness sends whole contexts, order of 1 MB): **32 MiB per request** (head and body), **64 MiB buffered over all connections**, **4 concurrent connections** (the harness opens one). A request past the first two is a named `413` and a closed connection; a connection past the third is a `503`. The box itself, also provisional: **1024 tasks** (processes and threads together) and **4 GiB** of memory, with no swap, in the box's own systemd user scope. They are constants in the launcher; the launch line records every effective value. Change them from measurement, in the launcher, never from a run script. |
| `SANDBOX_TEST=1`, `SANDBOX_TEST_EXEC` | Tests only: run that shell command inside the same box instead of the binary, after every check and mount. None is read outside test mode. |

Class rules, one function for the slot, each root and each entry, generated from the host at run time (no path is named in the launcher): refused when the path is `/`; is equal to or an ancestor of ANY home directory in the account database (all users, not only the invoker) or of the slot; contains the pinned binary (an RW root, RW entry or the slot; an RO root too); is equal to, contains or lies inside a `SANDBOX_PROTECT` path; touches a path the box itself provides (next paragraph); or lies below a home directory through any path component that begins with `.` (dot-directories hold secrets, ssh keys, config and the ENGRAM home). An entry outside its root is refused. The round-2 hand-listed protected paths are gone.

The box's own paths are ONE list in the launcher (`BOX_RO`, `BOX_PSEUDO`, `BOX_SHM`, `BOX_TMPFS_BIG`, `BOX_TMPFS_SMALL`, `BOX_ABSENT`, plus the directory the bridge socket is created in): the `bwrap` argument list is built from those arrays and the refusal reads the same arrays, and the launch line logs them as `box_paths=`. A cell compares that set with the destination paths of the argument list a dry run builds, so a mount added to one without the other goes red. For the system directories (`/usr`, `/bin`, `/sbin`, `/lib*`, `/etc`, `/proc`, `/dev`, `/dev/shm`, `/run`, and `/sys`, which the box leaves out) a slot, root or entry that is equal, inside or an ancestor is refused: a bind there would shadow the box's own mount (a slot of `/etc` re-exposes the host's real `/etc`; one under `/run/user` shows the user's sockets). For the fresh tmpfs directories (`/home`, `/tmp`, `/var/tmp`) and the socket base, only equal or an ancestor is refused: a bind placed beneath a fresh tmpfs shows only what the caller named, and the study's own slots and the tests live under `/tmp`.

Refusals (exit 2, one named line on stderr, nothing started or created): a missing or empty variable, a malformed hash or port or host, a port below 1024, a malformed or missing `SANDBOX_MODEL_ALLOW`, a malformed `SANDBOX_MODEL_LEARN` or learn mode without `SANDBOX_LOG`, a missing, empty, relative or non-existent `SANDBOX_PROTECT` entry, a slot that is not a directory or breaks a class rule, a `HOME` that is unset, empty or does not resolve to the slot, a missing binary, `bwrap` not on `PATH`, `systemd-run` missing or unable to start a user scope with the box's caps (the caps could not be applied, so nothing starts), a seccomp program that cannot be built or that `bwrap` does not accept (the box's key-syscall filter is required, so nothing starts), a `/usr/local` that exists but is not a plain directory (it could not be hidden), a hash mismatch, an extra-bind root or entry that breaks a class rule or lies outside its root, a missing root; in test mode, a malformed cap override.

Inside the box: `/home`, `/tmp`, `/var/tmp` and `/run` are fresh tmpfs (capped: `/tmp` and `/var/tmp` 2 GiB each, `/home` and `/run` 64 MiB each); `/dev` is bwrap's own tmpfs (half of host RAM, uncapped by bwrap), so `/dev/shm` is a separate tmpfs with the `/tmp` cap and `/dev` is then remounted read-only, so the study lead's home, other homes, host sockets and the dataset path are invisible; `/usr`, `/bin`, `/sbin`, `/lib*` and `/etc` are visible read-only, plus the slot (read-write), the binary file (read-only) and any validated extra binds. `/opt` is NOT bound: no cell needs it and the real pinned binary runs without it; if the engram arm's stack lives under `/opt` the run script must bind it with `SANDBOX_RO_BINDS`. `/usr/local` is NOT visible either: it holds host tooling, some of it naming a home directory and an account, and the student needs none of it (its interpreters and the model bridge are elsewhere). It sits inside the read-only `/usr` bind, which `bwrap` cannot subtract from, so the box shows an empty read-only tmpfs there: the directory exists and holds nothing (`BOX_HIDDEN_EMPTY` in the launcher). `/etc` stays, minus what names other people: `/etc/passwd` and `/etc/group` are synthetic (root and the invoking uid and gid only; the invoker's home is the slot), `/etc/machine-id` is a fixed zero id, `/etc/hostname` is `sandbox` (the box has its own UTS namespace, so the kernel hostname agrees), and every other readable regular file under `/etc` whose content contains `/home/` or the name of any account with uid 1000 or above (nobody excluded) as a whole word, with any delimiter (a colon, a comma, a space, an equals sign, a quote, a line start; not preceded or followed by a letter or digit) is an empty file. System account names (uid below 1000) are not matched; short names over-mask, which fails closed. The set is found by scanning `/etc` at launch; the launch line carries its COUNT only. Plainly: `/etc` remains readable inside the box, minus the files that name people or agents; the synthetic `passwd` and `group` name the invoking account, by design. Symlinks are not followed (a symlink under `/etc` that resolves into a system directory shows that file as it is), and an overlay applies only where the host file exists. No host process is visible (own `/proc`), `--die-with-parent` and `--unshare-pid` end every descendant with the box, every capability set is empty (`--cap-drop ALL` is in the argument list explicitly, so the boundary does not rest on `bwrap`'s default), and the environment is exactly what the caller passed minus `SANDBOX_*` (`HOME` is the slot: the wrapper refuses unless it is). Anything else the student must reach has to sit under the slot, in a system directory, or be bound explicitly (next paragraph); a path elsewhere is invisible by design.

The proctor channel: `feed4.py` puts its tools directory (where `ask-proctor` lives) on the student's `PATH` and sets `PROCTOR_DIR=<run out>/proctor`; both are outside the slot. The run script must therefore set `SANDBOX_RO_BINDS=<the tools directory>` with `SANDBOX_RO_ROOT=<its parent>`, and `SANDBOX_RW_BINDS=<the proctor directory>` with `SANDBOX_RW_ROOT=<the run's output directory>`, for the same launch, so `ask-proctor` runs from inside the box and writes only into the proctor directory. A cell runs a stub `ask-proctor` from a read-only-bound directory on `PATH` and checks that it writes into the read-write proctor directory on the host.

Network: a new namespace with loopback only. One forwarder inside listens on `127.0.0.1:<SANDBOX_MODEL_PORT>` and relays raw bytes over a UNIX socket bind-mounted from outside; a second, the outer forwarder, started by the wrapper and gone when the box exits, is trusted and is an HTTP request allow-list: it parses HTTP/1.1 requests on each connection (request line and headers; bodies by `Content-Length` or strictly chunked; keep-alive and pipelining, every request checked, not only the first), forwards a request only if its METHOD and decoded path are on `SANDBOX_MODEL_ALLOW`, and answers any other with `403` and a closed connection, so it never reaches the model server. A request it cannot frame (both length and chunked, two different lengths, line folding, a bare CR or LF in the head or in any chunk framing, an unsupported transfer coding) gets `400`, and so does any chunk extension, any whitespace in a chunk-size line, a chunk not ended by CRLF exactly, and any trailer: the last chunk is followed by the empty trailer only. NOTHING of a request reaches the model server until the whole request has validated: the request line, the headers, the framing and the body are read into memory first, under the caps above, and only then sent, in one piece. So a request refused at any stage (bad framing after an allowed head, a body over the cap, a client that hangs up inside a body) sends nothing upstream, not even its head, and one refused after its body was read closes the connection and logs one tagged line (cells record the bytes a recording upstream receives). The price is that a request is held in the host-side forwarder's memory, which is why it is capped on its own side: the forwarder runs outside the box and outside the box's caps. Only `HTTP/1.1` is served: a request line whose version is anything else (`HTTP/1.0`, `HTTP/2.0`, `HTTP/1.2`, ...) gets `505` and nothing reaches the model server; a request line that is not shaped like HTTP at all gets `400`; a request carrying `Expect: 100-continue` (the token, any case) gets `417` at once, because the head is otherwise held until a body the client is waiting for permission to send; a client that sends nothing, or stops inside a request, for `cap_read_idle_s` seconds (provisional, 120; the launch line records it) gets `408` and a closed connection, and the clock does not run while the bridge waits for the next request on a connection whose response is still streaming; a connection to the model endpoint that cannot be made gets `502` (below); `CONNECT`, an `Upgrade` header and a `Connection` that carries the token `upgrade` (checked independently, any case, anywhere in the comma list), and a target that is not origin-form (a path-absolute with an optional query) or holds a `#` get `403` (the checked string is the sent string: a fragment is never matched and then forwarded); a path with a `.` or `..` segment, an empty segment, a backslash, a control character or a second layer of percent-encoding never matches. Responses, streamed ones included, are relayed byte for byte. What the allow-list does NOT cover: it decides by method and decoded path only. It does not inspect bodies or query strings, so whatever an allowed request carries reaches the model server, and `SANDBOX_MODEL_ALLOW="POST /*"` allows every POST. Limit: a refusal of the second of two PIPELINED requests is written after the first request's response has been relayed, never in the middle of it. No other loopback port and no external address is reachable.

Refusal lines: the four counts. Every place the bridge refuses a request, or cannot serve one for its own reasons, writes EXACTLY ONE line to `SANDBOX_LOG`, at that place, and closes the connection; nothing is inferred later from `fwd-conn` lines. The line is `<prefix> method=<M> path=<P> status=<S> bytes_read=<N> kind=<K> reason=<R> detail=<D>` (never a body or a query string). The prefix stays readable by kind (`fwd-deny` for `kind=rule`, `fwd-fault` for `kind=upstream`, `fwd-refuse` for the rest), but a reader counts by `kind=` alone. There are four registered counts, and a refused request is in exactly one:

| Count | How it is read | What it holds |
|---|---|---|
| RULE REFUSALS | `grep -c 'kind=rule'` | a request the bridge could frame and refuses by rule: method and path not on the allow-list, and the forms it never allows (CONNECT, Upgrade, `Connection: upgrade`, non-origin-form targets, fragments, paths that do not decode or have dot or empty segments, `Expect: 100-continue`) |
| FRAMING REFUSALS | `grep -c 'kind=framing'` | bytes the bridge cannot frame as an HTTP/1.1 request, including a version other than HTTP/1.1 |
| CAP REFUSALS | `grep -c 'kind=cap'` | volume and time limits: a head or chunk-size line over its limit, a request over the per-request or total cap, a connection past the connection cap, an idle read timeout |
| NETWORK-CAPABLE SHELL CALLS | counted from the transcript, not from this log | untouched here |

`kind=upstream` is not a fourth bridge count and not a student attempt to be refused: it is a failure between the bridge and the model endpoint, and EVERY such line is counted and read by hand (the descriptive UPSTREAM ERRORS breakdown). Principle: an event is a harness fault only if the student cannot cause it; anything the student can cause is counted and reported, never flagged, re-run or excluded. A student can cause some of these (a request body the endpoint rejects early makes the send fail), so NO upstream reason flags a run by itself. The reasons: `connect-failed` (`502`: the bridge could not connect), `send-failed` (`status=-`: sending the request failed and the endpoint had not answered this request; no reply is attempted, because the relay has usually ended the client's side already), `rejected-early` (`status=unknown`: the send failed after the endpoint had already answered this request; the line carries the request bytes attempted and sent and the response bytes relayed; no reply from the bridge, the endpoint's own response already went through), and `upstream-reset` (`status=-`, written once by the relay: the endpoint's connection failed while a response was being relayed). The `status=` field means what the client received for this request, as far as the bridge knows: the bridge's own refusal status for a refusal; `-` when the client received nothing from anyone (`send-failed`, `upstream-reset`); `unknown` when the endpoint's own response reached the client but the bridge, which relays bytes without parsing them, does not know its status (`rejected-early`). A reset the relay sees while the current request has not finished being sent, with no response bytes relayed for it, is named `send-failed`, not `upstream-reset`: the relay does not name a failure while a request is being sent, it leaves it to the send site, which knows how far the send got. A failure on the CLIENT's socket (a hangup, a reset) is none of these and writes no tagged line, and neither is a reset the endpoint gives in answer to the bridge's own close of its connection. The failures are told apart by where they happen, never by the exception type.

The one flag, the harness fault, is read from the LOG, not from any upstream line: the outer forwarder writes ONE positive marker line, `fwd-first-request`, the first time a send actually moves any of a request's bytes upstream (a connect followed by a send that moves nothing does not count; once per launch, across connections, under a lock), and the run script must call the `log-verdict` subcommand (`python3 sandbox-forward.py log-verdict --log FILE`), the only place the rule lives: it prints `flagged: endpoint unreachable, nothing reached it` if the log has at least one `reason=connect-failed` line and no `fwd-first-request` line at all (the endpoint was never reachable), and `not-flagged` otherwise (exit 0 either way: the verdict is the output). A missing, empty or unreadable log is a named refusal (exit 2): no log is not 'no marker'. It reads line kinds and reasons only, never a body. Mid-run endpoint death (a connect that fails after a request reached the endpoint) is never an automatic re-run: the design owner decides before anyone has read that run's answers, the same rule for both arms (preregistration, section 14). The per-reason breakdown below is description for the report, not a new registered outcome. The `503` for a connection past the cap is refused at accept, before any request is read, so its line carries only what is known then: `method=- path=-`, `bytes_read=0` and the cap in `detail`; nothing is invented. A refusal that happens before the request line is parsed (a bad head, a read timeout) likewise has `method=- path=-`.


The rule is one log per launch. The wrapper APPENDS to `SANDBOX_LOG`, so two launches on one log would merge, and the first launch's `fwd-first-request` would hide the second's unreachable endpoint. The run script must therefore give each launch a fresh `SANDBOX_LOG` (`sandbox_launch.py` does, next section), and `log-verdict` refuses (exit 2, nothing on stdout) unless the log holds exactly one line starting `wrapper-launch ` (at column 0: the token and one space; a request path is logged after `method=`, so a client cannot make such a line). The message names the line it wanted and the count it found, for example `student-sandbox: refused: log-verdict: expected exactly one line starting 'wrapper-launch ', found 2`. A log written by the forwarder alone (no wrapper) has none and is refused. The refusal is a harness setup error, never a verdict on the run.

Two stated limits of the reset lines, both descriptive: nothing flags on either. (1) Once the bridge has sent its own FIN to the endpoint (the client half-closed), a later reset from the endpoint is not logged, by design since round 10 (our FIN could have provoked it), so a half-closing client hides a real mid-response reset; the zero upstream lines it leaves are pinned by a test. (2) the marker write is swallowed on an `OSError`, like every log write, so a false flag needs the marker write to fail while a LATER `connect-failed` line write succeeds (for example the disk fills, then frees), with an endpoint that died after a successful first request.

Order, as found in the code (the code's order is the rule; no check is reordered): a request is counted by the FIRST refusal the bridge makes for it, in this order: (1) connection cap, at accept (`503`): `connection-cap`; (2) head framing (`400` or `505`; a head over the size limit is a cap): `head-bare-cr-lf`, `head-too-large`, `request-line`, `version`, `obsolete-folding`, `header-line`, `header-control-char`; (3) body-header framing (`400`): `both-length-and-te`, `unsupported-te`, `content-length`; (4) rule checks, in this order: `connect`, `upgrade`, `expect-continue`, `target-form`, `fragment`, `path-undecodable`, `path-encoding`, `path-segment`, `not-on-allow-list`; (5) head size against the per-request and total caps (`413`): `request-cap`, `total-cap`; (6) the body, where `413` caps and `400` framing errors are refused in ARRIVAL order (the held-bytes caps `request-cap` and `total-cap` apply here too): `declared-length-over-cap`, `chunk-over-cap`, `request-cap`, `total-cap`, `chunk-size`, `trailer`, `chunk-framing`, `chunk-bare-cr-lf`, `chunk-bare-cr`, `chunk-line-too-long`; (7) the model endpoint, after the whole request has validated: `connect-failed`, `rejected-early`, `send-failed`. So a request carrying both `Expect: 100-continue` and a path not on the list is counted as `expect-continue` (`417`), because the `Expect` check runs before the allow-list. Every refusal closes the connection, so one request yields one line.

At any point: `read-timeout` (`408`, wherever bytes are awaited) and `upstream-reset` (written by the relay while a response streams, never by the request path).

The table and the order above are checked against the source by cells, not by a hand list. One cell reads every refusal site out of `sandbox-forward.py` with `ast` (a site without a kind or a reason, two sites sharing a reason, a status with no mapping, or a refusal reply or line built outside the two functions that own them, fails it), so a new refusal path cannot land in no count. A second cell parses THIS table and requires it to equal the source's set exactly (no missing row, no extra row, no differing kind or status). A third derives, with `ast`, the order in which the sites can be reached along one request (the accept hook, then the connection handler, with every helper expanded where it is called) and requires the order paragraph above to agree with it: each site in the README step that the source reaches it in, and the steps marked "in this order" token by token. It cannot see which branch a run takes, the arrival order of byte-driven checks inside the body, or sites reached only through a thread or callback (those the README lists under "At any point"). A fourth sends a request that fails two rule checks and requires the README's first-listed one to be the line it gets.

Limits of the bridge's tagged lines. The bridge relays response bytes without parsing them, so an upstream that closes CLEANLY in the middle of a response is indistinguishable from a normal close: the student's client sees a truncated reply, which shows in the transcript as an API error, and no line is written. Only resets and send failures are tagged. The short wait at the send-failure site (it lets the relay finish relaying an answer the endpoint already gave before the send is labelled) is not pinned by any cell, because the stub answers well before it resets; if it failed, the only effect would be `rejected-early` labelled `send-failed` in the descriptive count, never a flag. PIPELINING limit: the response byte count is per client connection, and a send failure is labelled by the growth of it since that request began to be sent, which is sound only when the client waits for each response; a student that PIPELINES two requests can make request 1's response bytes count as request 2's answer, so the label (`rejected-early` against `send-failed`) can be wrong. That is acceptable because neither reason flags a run: a wrong label can distort only the descriptive UPSTREAM ERRORS breakdown and nothing else. The idle read timeout does not run while a connection waits for its next request (so a streaming response is never cut), so an idle keep-alive connection is never timed, and stalled clients can fill the connection cap (4); that is inert for the harness's one client. Open question for the wrapper-cost pilot: whether the student's client ever opens a connection and leaves it idle before its first request (the clock does run then, and such a connection is cut at the idle timeout as `kind=cap reason=read-timeout`); the pilot's log answers it.

What the limits do and do not cover. The box's caps are PER BOX: the wrapper's own `exec` enters a transient systemd user scope (`TasksMax`, `MemoryMax`, `MemorySwapMax=0`, `OOMPolicy=continue`) around `bwrap`, so a fork bomb in the box hits `EAGAIN` at the box's own count while the host uid, the feeder and the host-side forwarder (started before the scope, so it stays in the caller's cgroup) keep forking and allocating, and a memory hog is killed by the kernel alone (the rest of the box carries on). They are not per-uid `rlimit`s, which were measured and set aside: `prlimit --nproc` around the wrapper makes the wrapper itself fail to fork when the uid already runs more threads than the limit (the limit is charged to the uid's host-wide count), `prlimit --nproc` inside the box does cap the box alone but limits no memory, and `RLIMIT_AS` is wrong for the memory cap (the pinned binary's runtime reserves about 9.4 GiB of address space for about 200 MiB resident). The scope caps both, and counts threads. Because the box moves into its own scope, a memory limit set around the whole run by the caller (for example `memrun`'s) no longer covers the box; the box's own cap replaces it, and the launch line records it. Not covered: CPU, disk-backed writes beyond the tmpfs caps, and system calls other than the key calls below: apart from them the kernel's whole unprivileged system-call surface is available inside the box, and `--cap-drop ALL` only removes capabilities. Kernel keys: the box may neither read nor write them. A key in the invoking uid's keyrings is readable from a user namespace that shares the uid (measured: the payload of a key in the uid's session keyring), and the uid's USER keyring belongs to the uid, outlives the run and is shared with the host seat, so a box that could write a key could pass state from one exam to the next. Clearing or replacing the session keyring would not close that (the user keyring stays reachable), and the host seat's keys must not be touched. So a small seccomp program, passed to `bwrap` with `--seccomp <fd>`, makes `keyctl`, `add_key` and `request_key` fail with `EPERM`; it is built in ONE function in `sandbox-forward.py` (`seccomp_program`, written by `sandbox-forward.py seccomp-bpf --out FILE`, commented line by line, no second copy) and checks the architecture first: anything but x86_64 is killed (`SECCOMP_RET_KILL_PROCESS`), and so is the x32 ABI on x86_64 (a syscall number with bit 30 set), so a 32-bit or x32 entry is no way around the number check. Every other system call is allowed. The program uses the x86_64 numbers, so the box runs on x86_64 only. The key listings in the box's own `/proc` (`/proc/keys`, `/proc/key-users`) name keys without any system call, so each is masked read-only with an empty file (`--ro-bind-data`: a bound `/dev/null` device file would answer every read with `EACCES` on the box's `nodev` `/proc`, measured). The wrapper builds the program, hands `bwrap` a descriptor, and before anything starts runs the same `bwrap` and program once around a command that does nothing; if the program cannot be built or `bwrap` does not accept it, the wrapper refuses (named, exit 2). `--unshare-cgroup` is not used, so `/proc/self/cgroup` inside the box shows the host's cgroup path (the box's scope name). The forwarder's exit check signals the watched pid (`os.kill(pid, 0)`), so a wrapper that has exited but whose parent has not yet waited for it counts as still there until the parent does.

If the outer forwarder is SIGKILLed it cannot remove its socket directory (`student-sandbox.*` under `TMPDIR`, holding `bridge.sock` and `watch.pid`). That is a small leak by design: the NEXT launch removes every such directory it owns (a real directory owned by the invoker, never a link) whose watched pid is gone, touching only those two files.

Cost (S8): `python3 sandbox-forward.py latency-compare --wrapper PATH/student-sandbox.sh -n N`, with the `SANDBOX_*` variables of a real launch set and a server answering `GET /ping` on the model endpoint (the boxed run lists exactly `GET /ping`, whatever the real launch lists), prints `direct`, `bridge` and `added` lines (median and max milliseconds over N one-connection requests). Cells: `tests/test_student_sandbox.py`; `SANDBOX_TEST_REAL_BINARY` and `SANDBOX_TEST_REAL_BINARY_SHA256` enable one cell that runs a real pinned binary's `--version` through the wrapper.

Cap hits after the run. `--collect` removes the box's scope the moment the box exits, so the counters are read while it runs: the outer forwarder (outside the box, alive for the whole run) finds the box's cgroup from the wrapper pid's `/proc/<pid>/cgroup` once the pid is in the named scope, reads `memory.events` (`oom_kill`, `max`) and `pids.events` (`max`) about once a second, and writes the `box-cgroup` line above at exit. A run whose line shows `oom_kill` above 0 or `pids_max_events` above 0 is a NAMED FAULT for the run script: the box hit its memory or task cap. The journal for the named unit (`journalctl --user -u <scope_unit>.scope`) is the cross-check for OOM kills (it records "A process of this unit has been killed by the OOM killer"; it records nothing for the task cap). Known limit: an event in the last poll interval before exit can be missed by the counters (the journal still records an OOM kill), and a run shorter than about a second may log `unavailable` or zero polls. The caps themselves (1024 tasks, 4 GiB) stay PROVISIONAL until the wrapper-cost pilot's learn mode has measured a real run with the recall service inside the box.

The box runs on the Linux study host only: the seccomp program carries the x86_64 syscall numbers and kills any other architecture. The cell that shows `/proc/keys` reading as zero bytes skips on a host with no keys, because the mask could not be told from the file's absence there.

### The launch module: `sandbox_launch.py` (the only door)

Standard library only. `run_feeder(py, feeder, argv, sandbox=..., log_dir=...)` is the one function through which a launcher starts a feeder (`FEEDERS` = `feed.py`, `feed2.py`, `feed4.py`, the one list of student-starting implementations). For a student session it does what the run script must do, so no run script has to remember any of it:

- **(a) a fresh `SANDBOX_LOG` per launch**: a path chosen for this session that does not exist before it (two sessions, two paths); a path that exists is a refusal;
- **(b) `log-verdict` after every student session**, both arms, setup sessions included (a setup session is just another student session through the module);
- **(c) a `log-verdict` exit 2 stops the caller** (`LaunchStop`, carrying the refusal's text); it is never read as not-flagged, and neither is any other unrecognised output;
- **(d) the verdict line is returned verbatim** (`result.verdict`), for the caller to copy into the run's record (`p1-session.py` writes it to `setup.txt`);
- **the wrapper**: a fresh directory holding `claude` (a COPY of `student-sandbox.sh`, not a symlink: the wrapper looks for `sandbox-forward.py` beside the path it was started as, and a copy cannot change under the run) and `sandbox-forward.py`, put FIRST on the `PATH` handed to the feeder, removed afterwards;
- **the feeder's PATH and environment are built by the module, nothing inherited (round 5b)**: the PATH is the prepared wrapper's directory first, then one fixed list of system directories (`FEEDER_SYSTEM_DIRS`; a floor for what the wrapper's children can reach, not the security line), and the environment is the allowlist `FEEDER_ENV_ALLOW` (`BEAM_OLLAMA_URL`, `BEAM_PARQUET`, each tied in the code to the line that reads it, pinned as a literal in a cell) taken by name from the caller's environment plus that PATH, so `LD_PRELOAD`, `LD_LIBRARY_PATH`, `BASH_ENV`, `NODE_OPTIONS` and every other name the caller set are absent (an allowlist, not a deny-list). The security line is the assertion that `claude` resolves, under that PATH, to the wrapper this launch prepared, plus a guard that no other directory of it holds an executable `claude`; both refuse before anything starts. The built PATH and the environment NAMES (never the values) are written to `setup.txt` (`sandbox feeder PATH:`, `sandbox feeder environment names:`). A failed exec of the wrapper (a missing interpreter, an invalid format) can no longer fall through to another `claude` from the caller's PATH (cells: a decoy `claude` on the caller's PATH whose sentinel is never written, for both failure kinds); and if a session ever ran without the wrapper anyway, there is no launch line, which is a `LaunchStop` and no answer is read (a cell at the stub feeder's `nowrapper` seam, which stands in for the exec because a stub starts no student). Limits: this covers a student session through the module; the `--dump-plan` call starts no student and still inherits the caller's environment; a test stub receives its own steering variables (`STUB_*` under `P1_FEED4`) through a test-only seam that a real feeder is refused.
- **the caller's `--env` pairs are an allowlist (A6)**: `feed4.py` and `feed2.py` put every `--env` pair into the student's environment, which is the environment the wrapper runs in, so the caller may pass only the keys of `FEEDER_ENV_PAIR_ALLOW`, defined once in `sandbox_launch.py` and pinned as a literal in a cell: `CLAUDE_CODE_MAX_CONTEXT_TOKENS` (`p1-session.py` passes it; the value must be digits only, a positive integer, no sign and no space) and `ANTHROPIC_BASE_URL` (read by `model_url`; the value must match the strict loopback form and `SANDBOX_MODEL_PORT`, as before). Every other key (`BASH_ENV`, `LD_PRELOAD`, `NODE_OPTIONS`, `PATH`, an unlisted name, a key with no `=`) is refused by name before anything starts, never silently dropped; a caller's `SANDBOX_*` pair stays refused, and the module's own `SANDBOX_*` pairs are added after the check. An `--env PATH=` therefore no longer replaces the built PATH (the code that honoured it is removed). The `--dump-plan` call starts no student and is not checked. Cells: `tests/test_sandbox_launch.py`, `test_a6_*`.
- **the settings as `--env` pairs**: `feed4.py` and `feed2.py` build the student's environment from scratch, so an exported `SANDBOX_*` variable is dropped and only a feeder `--env` pair reaches the wrapper (a cell shows the wrapper refusing an exported-only setting through a real `feed4.Student`). The module passes every setting the wrapper requires (`REQUIRED_SANDBOX`, which a cell compares with the set `student-sandbox.sh` refuses without), `SANDBOX_LOG`, and the proctor binds (`SANDBOX_RO_BINDS` = the feeder's directory with `SANDBOX_RO_ROOT` its parent; `SANDBOX_RW_BINDS` = `<out>/proctor` with `SANDBOX_RW_ROOT` = `<out>`);
- **named refusals before anything starts** (`LaunchRefused`, exit 2): the log path exists; the `claude` first on the `PATH` the feeder's `Popen` will use is not the prepared wrapper; a caller's `--env` pair whose key is not in `FEEDER_ENV_PAIR_ALLOW` (`PATH` included), or whose `CLAUDE_CODE_MAX_CONTEXT_TOKENS` value is not a positive integer in digits; the model URL the student will use (`--env ANTHROPIC_BASE_URL=`, else `BEAM_OLLAMA_URL`, else the default) is not loopback or its port is not `SANDBOX_MODEL_PORT`; a required `SANDBOX_*` value is missing; the expected-hashes file is missing or malformed; a caller passes a `SANDBOX_*` pair of its own;
- **the hash checks**: BEFORE the launch the module hashes the two copies it prepared and refuses, naming both values, if either differs from the expected value; AFTER the session it compares the launch line's `wrapper_sha256` and `forwarder_sha256` with the expected values and stops (`LaunchStop`, both values named) before any answer of that session is read. The second is the proof of what actually ran.
- a feeder call that starts no student (`--dump-plan`) runs through the same function with no wrapper and no log.

**Expected hashes.** The module takes the expected-values file as an explicit input (no default): two lines, `wrapper_sha256=<64 lower-case hex>` then `forwarder_sha256=<64 lower-case hex>`. The scored run passes `studies/beam-2026-11/data/sandbox-registered.txt`, which the study lead writes in the freeze PR (equal to the sha256 of the two files at the frozen commit; this PR does not create it, the wrapper not being frozen). A pilot passes its own file, written by the study lead from the commit the pilot runs.

**First consumer: `p1-session.py`**, which needs `--expect-sandbox FILE` and the `SANDBOX_*` settings in its environment for a real run (see its docstring) and records the log's basename, the verdict line verbatim and the two launch-line hashes in `setup.txt`. A log-verdict refusal or a hash mismatch is exit 3 with a `STOP:` line; `flagged` is recorded, not a stop.

**No second door (classified, fails closed).** A cell walks this directory (any extension, any shebang, outside `tests/`) and requires every file whose text mentions a feeder (`feed`, `feed2`, `feed4`) or the word `claude` to be exactly one of: the module; a feeder in `FEEDERS`; a file carrying the `RETIRED-LAUNCHER` marker in its first three lines; or a file listed in the module's one dict `NON_LAUNCHERS` with a one-line reason (files that only read a feeder's text or constants, or name `claude` in prose). A new or changed file that mentions them and is in none of these fails the cell, naming the file; a `consumer:` entry (`p1-session.py`) must also really call `run_feeder(` through the module, which is why the OLD `p1-session.py` (it started `feed4` through a variable-held path, the door the first search was blind to) fails the cell in a scratch tree. Adding a name to `NON_LAUNCHERS` is the review point: nothing else lets a launcher through. What this cannot see: a feeder or `claude` name assembled at run time (string concatenation, a variable, an environment value), a launcher in another directory, and a launcher hidden inside a file that is already listed. Cells: `tests/test_sandbox_launch.py`.

**Teardown: no box or bridge outlives its session (round 2).** Boxes and outer forwarders from the wrapper's own test cells were found alive, parent pid 1, up to about 20 hours old: a caller's SIGKILL does not always end the box. The mechanism is NOT proven (it is filed separately), so the wrapper is not relied on; the module's stop is the guarantee.
- The launch line carries three more fields, read after the forwarder is up so they are real: `forwarder_pid`, `forwarder_start` (field 22 of `/proc/<pid>/stat`, clock ticks since boot, which a reused pid does not share) and `bridge_sock` (the launch's socket path, unique per launch).
- After every session (whatever the feeder's exit code, and even if it raised) the module runs `systemctl --user stop <scope_unit>` and asserts nothing of the launch remains: (i) the scope's own cgroup is empty or the unit gone (the cgroup path is read from the unit); (ii) the forwarder pid is gone, or is a different process by start time (a forwarder that is still the same process is terminated, then re-checked); (iii) no process anywhere carries this launch's `bridge_sock` path as an argv element (an exact path, not a name). A leftover is a `LaunchStop` naming each pid and why it counts. A session whose log has no `wrapper-launch` line (the wrapper refused before launching) has nothing to stop: it is told apart by exactly that missing line.
- **Before any launch** the module refuses (`LaunchRefused`, a setup error, never a flag) while any earlier launch in the state directory fails those three checks, or any active user scope unit named `student-sandbox-*` exists (the wrapper names its units that way: a positive marker, not a process search). The refusal names each unit or pid and how to stop it. The state directory is supplied by the caller and has no default (`p1-session.py` uses `<BEAM_RUNS_DIR>/sandbox-launches/`): one JSON record per launch, written before the session starts and marked done after the teardown passes.
- A leftover found at a launch is reported per run as a count (`LaunchRefused.leftover_count`; `p1-session.py` writes `sandbox leftovers found at launch: N` to `setup.txt`). The plan text for what to do with a leftover comes in the freeze PR.
- The wrapper's own cells stop their scopes at teardown (`test_student_sandbox.py`'s `cfg` fixture; a unit counts as a cell's own when a process in its cgroup carries the cell's scratch root in its argv, never by a name pattern).
- Limit: a wrapper killed after it started the forwarder but before it wrote the launch line leaves a forwarder that no record names (its scope does not exist yet, since the wrapper starts it after the line). The module cannot see it; it ends by itself when the pid it watches is gone.

**Round 3 (reviewer fold and the security seat's bounds).**
- **The scope is always stopped when it is known.** Whenever a launch line names a `scope_unit` that is a name this wrapper makes (`<prefix><pid>-<hex>`, checked before anything is stopped, so an arbitrary unit is never stopped), the module stops it FIRST, whatever the other markers say and whether or not the launch record can be written. A forwarder marker that is 0 or missing (the wrapper writes `forwarder_start=0` if the forwarder died before its start time was read) means check (ii) could not run: the STOP says so; it is never read as clean. A launch line without `scope_unit` is a named STOP.
- **The teardown checks fail closed.** An unreadable or missing `cgroup.procs` while the unit still exists is a named STOP, not "empty" (only a unit that vanished between the two reads counts as empty). The before-launch scan queries every scope under the launch's prefix in any state (`systemctl --user list-units --type=scope --all '<prefix>*'`) and keeps every unit that is not `inactive` (activating, active, deactivating, and a failed unit that still holds processes).
- **Hermetic cells.** The before-launch scan is host-wide by design (a scored run must refuse while ANY earlier box is alive), so a cell would fail when another seat's box is up. The wrapper therefore accepts `SANDBOX_TEST_UNIT_PREFIX` ONLY with `SANDBOX_TEST=1` (a named refusal otherwise, and for a malformed value) and names its scope `<prefix><pid>-<hex>`; the module's scan and its unit-name check use the prefix of the launch (`student-sandbox-` in a real run, the only value there). Each test run gives itself a unique prefix. A real run has no override.
- **Limit (security seat, bound 2).** The before-launch scan names only units under the launch's prefix (`student-sandbox-` in a real run), so a leftover of an older build in an unnamed `run-*.scope` is outside it by construction. That is acceptable only while this module is the one door, which the classification above keeps so. Leftovers from before this module exist must be cleared by hand before the first scored run.
- **The planted-survivor control (K3).** A cell plants a process OUTSIDE the scope whose argv carries the launch's `bridge_sock` and shows the after-check names it; disabling check (iii) reddens it. Keep that cell.
- **A flagged continue-reading session (design owner's ruling).** `p1-session.py --continue-reading` still saves the end state after a FLAGGED session, but only under a quarantine name, `<--save-end-state>.flagged` (hashes `.flagged.hashes.txt`, record `.flagged.verdict.txt`), with the verdict line beside it, and the run record says in words that the run is excluded. The session's wrapper log, verdict line and transcript stay where the run record points. Every save path is created exclusively (never overwritten); on failure only what the run itself created is removed. The reader refuses BY CONTENT as well as by name: continue-reading refuses (exit 2, before anything is touched) an end state that sits under a quarantine name, or whose own record (`<end state>.verdict.txt`, a `sandbox verdict:` line) carries a flagged verdict, or that has no verdict line at all (a state saved by an older tool or copied by hand, including the original preserved end state until a record is written for it). Renaming a quarantined state together with its record does not launder it; renamed alone it has no verdict line.
- **A feeder's argv is default-deny (security seat's review).** `argparse` (the feeders use its defaults) accepts `--opt=value` and any unambiguous prefix (`--en`, `--ou`, `--arm-hom`) for the same option, while the module's guards read only the exact `--flag VALUE` spelling, so such a spelling would be applied by the feeder and be invisible to the PATH check, the model-URL check, the refusal of a caller's `SANDBOX_*` pair and the proctor binds. The module therefore keeps ONE dict, `FEEDER_OPTIONS = {feeder: {exact long option: arity}}`, and before anything starts refuses, naming the token, any argv token that is not exactly an allowed option or the value of one (an option is told from a value by position and the arity stated in the dict: after an arity-1 option the next token is its value and may not look like an option unless it is a plain negative number). That covers `--env=K=V`, abbreviations, short flags, positionals and any option a feeder adds later, by construction. `feed4.py`'s list is exactly what `p1-session.py` passes; `feed2.py`'s is what the retired `run-engram-full.sh` used plus `--env` (no in-tree launcher passes `feed2.py` through the module yet); `feed.py`'s is its first-turn options (and it declares no `--env`, which the module passes, so it cannot be launched through the module until it does). A test stub obeys the allow-list of the feeder it stands in for. **Adding a feeder option to a launcher requires adding it to `FEEDER_OPTIONS` in the same PR, or the launch is refused (loud, by design).** A cell checks every option in the dict against the feeder's own `add_argument("<option>"` line, by text, for both presence and arity.
- **What the no-second-door gate covers, and how it is run (round 4).** Its population is the files TRACKED by git under this directory (`git ls-files`, outside `tests/`), not a walk of the working tree: pytest writes `.pytest_cache/` into this directory, with node ids that contain `claude`, and a walk was green on a fresh checkout and red on every later run. If git cannot be run, the directory is not a git checkout, or no file is tracked, the gate is a named refusal, never an empty pass; a tracked file that is gone or unreadable on disk is a named violation ("cannot be judged"). **Limit:** an UNTRACKED new launcher file is outside the gate until it is added (a reviewer sees it in the PR diff; the gate itself has no clean-tree check, and none of the run scripts does either: `pilot-run.sh`, which had one, is retired). Planted-tree cells build a scratch tree outside git and pass their own file list (or `git init` the copy), so no cell enumerates the outer repository. The suite is run as CI runs it, WITHOUT isolation flags (no `-p no:cacheprovider`), at least once per head: the isolation flag is what hid this.
- **A stray test mode does not pass the door.** In a REAL run (the default) the module refuses, named and before anything starts, any `SANDBOX_TEST*` setting: `SANDBOX_TEST`, `SANDBOX_TEST_EXEC`, the cap knobs, `SANDBOX_TEST_ALLOW_BINARY_IN_RW`, `SANDBOX_TEST_UNIT_PREFIX`. A test run says so explicitly (`Sandbox(..., allow_test=True)`, which the cells pass; `p1-session.py` passes it only under the existing `P1_TEST_HOOKS=1` rule, no new switch). After every session the module reads `test_mode=` and `test_exec=` off the launch line, and in a real run anything but `0` (or a missing field) is a LaunchStop: the student ran in a test-mode box. The `cap_*` values on the launch line are returned (`result.caps`) and `p1-session.py` writes them, with `test_mode` and `test_exec`, to `setup.txt` (`sandbox launch-line cap_tasks: ...`).
- **The model URL is matched, not parsed.** The module accepts the URL the student will use ONLY in the strict form `^http://(127\.0\.0\.1|localhost|\[::1\]):<port>(/[A-Za-z0-9._~/-]*)?$`, with the port equal to `SANDBOX_MODEL_PORT`: no userinfo, no backslash, no percent-escape, no query, no fragment, no other scheme, no missing port. Parsing is the hazard: `http://evil.com\@127.0.0.1/v1` (with a port) has the host `127.0.0.1` for Python's `urlsplit` and `evil.com` for the WHATWG parser of the student (a Node program). A URL that does not match is refused whatever a parser would make of it.
- **What runs where (hosts with no systemd, no `/proc`: a Mac).** The module stops and lists scopes through `systemctl --user` and reads `/proc` (start times, argv scans). Three kinds of cell, by name: (1) cells that need a REAL user manager (real scopes and boxes) carry `needs_box` and skip without one; (2) cells that run a student session through the module (the stub feeder and the stub wrapper's launch line read `/proc`) carry `needs_linux_wrapper` (`tests/conftest.py`) and skip on a host without `/proc`, with the same reason string as `needs_box`; (3) every other cell, the pure ones (settings, expected-hashes file, argv, URL pattern, the no-second-door gate) runs everywhere, against a stand-in `systemctl` (`tests/conftest.py`, `install_stub_systemctl`) that answers as an empty user manager. Measured by simulation on Linux with no `/proc` (an empty tmpfs over it) and `systemctl`, `systemd-run` and `bwrap` removed from the PATH the tests see: 0 failures over all four BEAM tool test files: `test_sandbox_launch.py` 153 passed / 47 skipped, `test_p1_session.py` 110 / 36, `test_p1_continue_reading.py` 72 / 34, `test_pre_module_start.py` 29 / 5. The earlier 170 / 182 figure was Linux with only `systemctl` removed, NOT a Mac: it still had `/proc`, which is why it hid the cells that fail on one. A real Mac ran the whole `tools/tests` at 7b6402e8 and found three unmarked cells (3 failed, 937 passed, 448 skipped); the marking in this round is the fix (every cell that runs the stub feeder, or otherwise reaches a `/proc` read, now carries the marker), and a re-run on the Mac is the colleague's.

- **Test hooks and the scored launcher.** A stray `P1_TEST_HOOKS=1` together with a stray `SANDBOX_TEST*` setting passes BOTH gates by design: the module's real-run refusal is lifted for a test run, and `p1-session.py` passes `allow_test` exactly when `P1_TEST_HOOKS=1`. Test mode is then recorded (`setup.txt` carries `sandbox launch-line test_mode:` and `test_exec:`, and the launch line itself says `test_mode=1`). The guard is procedural: a scored launcher never sets `P1_TEST_HOOKS`.
- **PATH resolution rule.** The `claude` the feeder's `Popen` will start is resolved the way `Popen` does, from the PATH the feeder builds (the module's built one; a caller's `--env PATH=` is refused, not honoured): entries in order, the first executable regular file named `claude` wins; an EMPTY entry is the child's working directory (`<arm-home>/work`) and a relative entry is relative to it. A cell runs the real `Popen` with the same PATH and cwd to show they agree.
- **A pre-module end state is a PILOT start only (design owner's ruling).** Every end state saved before the sandbox existed has no verdict record, so continue-reading refuses it. The wrapper-cost pilot needs exactly such a start, so there is one narrow way in, and it is never on a scored path.
  - **The command.** `python3 mark-pre-module-start.py STATE --by NAME` prints STATE's store content hash (the existing helper, `protected_store_hash` in `p1-session.py`: no second hash) and writes `<STATE>.verdict.txt` by exclusive create with exactly four lines: `sandbox verdict: none (pre-module state, never wrapped)`, `state_sha256=<hex>`, `marked_by=<NAME>`, `marked_at=<UTC ISO>`. It refuses (exit 2, named, nothing written) an existing record, a state that already has any verdict line, a STATE that is not an existing directory or has no readable store, and an empty `--by`. Nothing calls it automatically: a cell fails if any tracked non-test, non-markdown file under this directory names the command anywhere, other than the command itself and `p1-session.py`'s comment and help text (it sees a name spelled out, split over lines or not; it cannot see a name assembled at run time).
  - **Who may run it.** The study lead, once per run, naming the state. Marking is the act of deciding "this state is a pilot start"; no tool, launcher or script does it on anyone's behalf.
  - **The pilot-only rule.** The default reader (`end_state_verdict_problem(path)`, what any scored launcher calls) REFUSES the `none (pre-module ...)` line, named. Only `p1-session.py --continue-reading --pilot-pre-module-start` passes the allowance (the flag is refused without `--continue-reading`). When accepted, the reader re-hashes the state's STORE (`knowledge.db` table contents, the existing `protected_store_hash`) and refuses unless it equals the record's `state_sha256` (a store changed after marking is not the store that was named; memory files, `.claude/` and hooks are NOT covered by this hash), and the run's `setup.txt` carries `pilot, pre-module start` and `pre-module start state_sha256: <hex>`. In plain words: `state_sha256` binds the store, not the home; what the record proves is that the `knowledge.db` store is the one that was named, and nothing about the rest of the home. Whenever the flag is passed, whether or not the state is pre-module, `setup.txt` also carries one line, `pilot flag passed: --pilot-pre-module-start`, so a later ingest can refuse on the flag itself (cells: `test_f2_*`). A state with no verdict line at all is still refused everywhere. A flagged record, or a record that mixes the pre-module line with another verdict line, is refused even with the flag.
  - **Why.** A scored run must start from a state whose whole history ran inside the wrapper. A pre-module state cannot meet that, and a pilot measures the wrapper's cost rather than answers, so it may start from one, but only when someone named it on purpose, and the record shows it.
  - **What the scored path must do (a requirement, not yet code: no scored launcher or result ingest exists in this tree).** The scored launcher must never expose `--pilot-pre-module-start`, and whatever ingests a scored run's result must refuse a run whose `setup.txt` carries `pilot, pre-module start` (or the `pilot flag passed` line). Until that ingest exists the guard is the default reader, the launch module's text (a cell), and the launcher review. `p1-session.py` itself refuses the flag outside `--continue-reading` and does not accept an abbreviation of it (a cell).
  - **A scored launcher must never expose the flag.** The launch module (`sandbox_launch.py`) does not know it (a cell checks the text). The no-second-door cell and the launcher review are where that is checked: a launcher that forwards `--pilot-pre-module-start`, or wraps `p1-session.py` with it set, is a second door.
- **The launch log has three states, and one limit (design owner's finding).** `read_launch_fields` tells apart a log that is ABSENT (the wrapper refused before it made one: the record is closed, nothing to stop), a log with NO launch line (written by the forwarder alone: closed, nothing to stop), and a log that is PRESENT BUT UNREADABLE (permission, a directory, an I/O error: nothing is known). The last is never closed as "never launched": the before-launch check refuses by name (the record stays open) and the close after a session is a named `LaunchStop`. Cells: `tests/test_sandbox_launch.py`, `test_l_*`. **Limit:** a forwarder started by a launch that died before its launch line was written is invisible to the module, because no marker for it exists anywhere; that is one reason a seat that is not itself launching sweeps the host (scope units, bwrap and forwarder processes) before a scored run.
